# UWB Data Logger Project

## 1. 项目概述

这是一个基于 `STM32H743VITX` 的嵌入式数据采集工程，当前目标是把以下多源传感器数据统一采集并写入 `SD` 卡：

- `DW1000` UWB 测距数据
- `GNSS` 定位与时间信息
- `IMU` 原始加速度/角速度数据

当前工程已经具备基础运行框架，使用：

- `STM32CubeMX` 生成底层初始化代码
- `HAL` 驱动外设
- `FreeRTOS` 组织任务
- `FatFs` 访问 SD 卡
- `EIDE` 作为当前工程构建入口

这个 `README` 的目的不是描述“理想架构”，而是尽量准确记录**当前代码现状**，作为后续重构的基线文档。

---

## 2. 当前实现目标

从现有代码看，工程当前主要承担以下职责：

1. 初始化 STM32H7 基础外设和 RTOS 环境。
2. 根据 Flash 中保存的设备配置，决定本机运行角色：
   - `Tag`
   - `Anchor`
3. 采集并组织三类数据：
   - `DW1000` 双向测距结果
   - `GNSS` 解算结果与时间基准
   - `IMU` 原始传感器数据
4. 通过统一时间戳对多源数据进行粗同步。
5. 将采样结果以文本日志形式写入 SD 卡文件 `data_log.bin`。

## 3. 硬件与接口现状

### 3.1 主控

- MCU：`STM32H743VITX`
- 时钟源：当前 `SystemClock_Config()` 使用 `HSI + PLL`

### 3.2 外设分配

#### 串口

- `USART1`
  - 波特率：`460800`
  - 引脚：`PA9/PA10`
  - 当前用途：日志输出与调试接口
  - 说明：该接口作为主调试串口保留

- `USART3`
  - 波特率：`460800`
  - 引脚：`PB10/PB11`
  - 当前用途：`GNSS` 主数据输入口
  - 接收方式：`DMA + IDLE` 中断

- `UART4`
  - 波特率：`115200`
  - 引脚：`PA0/PA1`
  - 当前用途：预留调试串口
  - 说明：当前主业务链路未使用，作为硬件调试冗余接口保留，用于异常情况下的辅助接入

#### SPI

- `SPI1`
  - 引脚：`PA5/PA6/PA7`
  - 连接设备：`ASM330` IMU
  - 片选：`PC4`
  - 说明：该接口用于 IMU 数据采集。虽然在 `.ioc` 中配置了 DMA 相关内容，但当前实际采样流程暂未使用 DMA，之后重构也不需要DMA

- `SPI2`
  - 引脚：`PB13/PB14/PB15`
  - 连接设备：`DW1000`
  - 片选：`PB12`
  - 复位：`PD9`
  - 中断输入：`PD8`
  - 说明：该接口计划切换为 DMA 方式，主要考虑后续可能在数据链路层读取 `CIR` 数据，用于 `NLOS` 判定与信道质量分析

#### I2C

- `I2C1`
  - 引脚：`PB6/PB7`
  - 当前状态：已完成初始化
  - 当前用途：尚未接入主业务链路
  - 说明：该接口暂作为预留资源保留，后续根据重构需求决定是否纳入正式功能

#### SDMMC

- `SDMMC1`
  - 工作模式：`4-bit`
  - 引脚：
    - `PC8/PC9/PC10/PC11`
    - `PC12`
    - `PD2`
  - 说明：除标准 `SDMMC` 信号外，硬件还包含一个卡检测引脚 `PB5`，用于检测 SD 卡是否插入

### 3.3 外部中断与辅助信号

根据 `HAL_GPIO_EXTI_Callback()` 当前代码，系统已接入以下外部中断或辅助输入信号：

- `PA4`：IMU 数据就绪中断
- `PD8`：DW1000 中断输入
- `PC0`：GNSS `PPS` 时间同步输入
- `PE2`：用户按键 `USER_KEY`
- `PB5`：SD 卡检测输入


### 3.4 指示灯

- `PE4 -> LED0`：低电平点亮
- `PE5 -> LED1`：低电平点亮
- `PE6 -> LED2`：高电平点亮
- `PC13 -> LED3`：高电平点亮

说明：指示灯的有效电平并不统一，后续重构时应将其抽象为统一的 `LED` 控制接口，避免在业务代码中直接依赖高低电平语义

## 4. 软件架构要求

这一节定义后续重构时的软件组织原则。核心要求只有一条：凡是由 `CubeMX`、`HAL` 或第三方官方库生成/提供的代码，原则上不直接改动；重构重点集中在自研业务代码，尤其是 `APP/` 目录。

### 4.1 重构基本原则

后续代码整理应遵守以下原则：

1. `Core/`、`Drivers/`、`Middlewares/`、`FATFS/`、`Thrid/` 中的官方代码、第三方代码以及 `CubeMX` 生成代码，原则上不直接修改。
2. `main.c`、`freertos.c`、`stm32h7xx_it.c` 这三个文件允许根据工程需要进行调整，但应仅保留启动入口、任务创建入口和中断分发入口，不在其中堆积业务逻辑。
3. 允许放在 `main.c`、`freertos.c`、`stm32h7xx_it.c` 中的内容，应尽量采用“外部封装 + 本地调用”的形式组织，也就是这些文件只负责调用清晰的接口，不负责承载复杂实现。
4. 所有可维护、可重构的业务逻辑统一集中到 `APP/` 内部完成，避免业务逻辑继续分散到自动生成代码目录中。
5. `APP/` 目录必须按职责划分，避免按临时需求或单次功能开发随意堆放文件。
6. 任务调度、设备适配、公共服务、业务逻辑必须分层组织，减少跨层直接调用，避免后续修改时互相牵连。
7. 中断入口文件仍然保留在 `stm32h7xx_it.c` 中，这是工程结构的一部分；但中断处理代码应保持简洁、明确，优先采用“状态采集、事件标记、接口转发”这种方式组织，避免在中断中直接堆积复杂处理流程。
8. 后续重构的目标不是追求目录数量，而是优先建立清晰、稳定、易维护的工程边界。

### 4.2 对现有目录的定义

当前工程中各顶层目录的角色建议明确如下：

- `Core/`
  - `CubeMX` 生成的启动文件、外设初始化代码、IRQ 入口
  - 原则：只保留底层初始化和必要的用户挂接点，不承载复杂业务逻辑

- `Drivers/`
  - `HAL/CMSIS` 官方驱动
  - 原则：不修改

- `Middlewares/`
  - `FreeRTOS`、`FatFs` 等中间件源码
  - 原则：不修改

- `FATFS/`
  - 这是 `CubeMX` 生成的 `FatFs` 集成层与目标板适配层，不是手工外部导入目录
  - 从文件头和生成模板可以确认，`FATFS/App` 与 `FATFS/Target` 都属于 ST 的生成内容
  - 原则：尽量不直接修改，如需扩展存储策略，应在 `APP/` 内部封装

- `Thrid/`
  - 用户引入的第三方驱动库
  - 当前主要包括 `ASM330` 官方驱动和 `DW1000` 官方驱动
  - 原则：尽量不改；如有适配需求，在 `APP/` 中增加包装层

- `APP/`
  - 这是后续重构的核心区域
  - 所有自研逻辑、任务编排、设备封装、公共服务都应统一在这里整理

### 4.3 APP 目录重构目标

`APP/` 目录后续不建议继续按当前这种“边写边堆”的形式维护，而应整理为几个较稳定的大类目录。这里不追求过细拆分，先采用更适合工程落地的中等颗粒度结构。

建议采用以下目录层级：

```text
APP
├─ bsp          // 板级适配：LED、按键、EXTI、中断转发、片选/复位等
├─ common       // 通用头文件、公共类型、日志、通用工具
├─ device       // 设备适配：UWB、IMU、GNSS、SD 等硬件/协议封装
├─ service      // 公共服务：配置、时间同步、数据缓存、存储管理
├─ task         // FreeRTOS 任务及任务编排
└─ app          // 系统业务入口、角色逻辑、整体流程控制
```

### 4.4 各目录职责说明

- `APP/bsp`
  - 只负责板级资源抽象
  - 包括 GPIO 控制、外部中断转发、LED/按键控制、设备片选/复位等
  - 不承担协议解析和业务状态机

- `APP/common`
  - 放置公共类型、公共宏、基础工具函数
  - 可保留日志接口、环形缓冲区、通用时间类型等通用内容
  - 原则上不耦合具体外设

- `APP/device`
  - 负责各设备的驱动适配与协议封装
  - 推荐将当前的 `UWB`、`GNSS`、`IMU`、`SD` 相关设备接口都整理到这里
  - 这一层关注“设备怎么用”，不负责系统工作流

- `APP/service`
  - 放置跨模块的公共服务能力
  - 例如：配置管理、时间同步、数据汇聚、存储调度
  - 这一层是任务层和设备层之间的缓冲层

- `APP/task`
  - 只保留 FreeRTOS 任务函数、队列和通知组织
  - 不建议在这里堆积过多设备细节和协议处理逻辑

- `APP/app`
  - 放系统整体流程
  - 包括 `Tag / Anchor` 模式切换、系统启动流程、工作状态组织
  - 这是最接近最终产品行为的一层

### 4.6 源码保全策略

由于本次重构大概率会对 `APP/` 下的大部分内容进行重新整理，因此不再强调逐文件迁移建议，而是优先保证原始代码可回溯、可对照。

建议在正式重构前增加一个源码保全目录：

```text
APP-copy/
```

使用原则如下：

- 在开始重构前，将当前 `APP/` 目录完整复制到 `APP-copy/`
- `APP-copy/` 仅作为重构前源码快照，不参与后续正式架构设计
- 后续如需回溯旧实现、比对接口、核对细节，可直接参考 `APP-copy/`
- 当新架构稳定、旧代码不再需要时，再统一删除 `APP-copy/`

这样处理的目的，是在大范围重构过程中保留一份可直接查阅的原始版本，避免后续追踪某段旧逻辑时找不到对应源码。

### 4.7 这一版目录设计的目的

这一版目录设计不是为了追求一次性完成“最标准”或“最细粒度”的工程划分，而是为了配合当前的重构节奏，先把大的方向定义清楚。

当前更合适的推进方式是：

- 先明确主目录职责
- 先把工程边界划清楚
- 先让文档结构保持可读、可确认
- 再逐步推进具体实现和后续细化

也就是说，这一版更强调“分阶段调整、逐步落地”，而不是一次性把文档和代码结构改得过大、过深，导致阅读和确认成本过高。

### 5.1 总体阶段划分

从当前代码结构来看，系统运行可以先粗分为三个阶段：

1. `Boot` 阶段
   - 完成 MCU 复位后的基础初始化
   - 建立最小可运行环境

   - 初始化 RTOS
   - 启动各业务任务

### 5.4 三种运行状态说明

#### 1. Boot

`Boot` 定义为系统上电后的起始阶段。当前在本章中先不展开底层初始化细节，而是把 `Boot` 视为系统进入不同工作模式之前的统一入口状态。

当前先明确 `Boot` 阶段的行为：

1. 系统一上电，即进入 `Boot`
2. 进入 `Boot` 后，先将 `LED0`、`LED1`、`LED2`、`LED3` 全部熄灭
3. 在 `Boot` 阶段检测 `USER_KEY` 是否处于按下状态
4. 若检测到按键按下，则进入 `配置模式`
5. 若检测到按键未按下，则进入 `运行模式`

因此，`Boot` 当前的核心职责是完成启动后的统一状态收敛，并决定后续进入哪一种工作模式。

#### 2. 配置模式

配置模式是在 `Boot` 阶段检测到按键按下后进入的专用工作模式。该模式的主要用途是设备参数配置、配置确认和 Flash 写入，并且当前按你的要求，配置模式仍然进入 `RTOS` 环境执行。

当前先明确配置模式的主流程：

1. `Boot` 阶段检测到 `USER_KEY` 按下
2. 系统切换进入 `配置模式`
3. 进入配置模式后，使用 4 个指示灯给出视觉提示
4. 通过 `USART1` 接收配置命令
5. 通过串口命令完成配置接收、读取和 Flash 写入
6. 支持按键短按/长按的辅助控制逻辑

##### 进入指示

配置模式下，4 个指示灯按固定顺序循环闪烁，用于表示系统已进入配置状态：

- 顺序：`LED0 -> LED1 -> LED2 -> LED3`
- 方式：依次单灯闪烁
- 间隔：`200 ms`

这一组流水灯当前只承担“进入配置模式”的状态指示功能，不承担复杂编码含义。

##### 配置数据组织

当前配置数据改为拆分成两个独立结构体，分别用于持久化参数和静态系统参数。

##### 1. Flash 持久化配置结构体

这一部分作为写入 `Flash` 的配置参数，只保留设备运行所必需、并且需要在配置模式下修改的内容。

建议至少包含：

- 短 `PAN` 地址
- `ID` 地址
- 当前角色：`Anchor` / `Tag`

这部分参数通过串口命令配置，并最终写入 `Flash`。

##### 2. 静态外参结构体

另一部分参数单独放在 `.h` 文件中，以静态变量的形式存在，由系统直接读取使用，不写入 `Flash`。

这一部分主要用于：

- 不需要在现场频繁修改的参数
- 与设备角色无关、但与系统运行有关的固定参数
- `UWB` 的扩展配置或其他工程级静态参数

也就是说，当前配置设计改为：

- 基础设备配置：写入 `Flash`
- 外部扩展参数：保存在头文件静态变量中，由系统直接调用

这样拆分后，配置边界会更清晰：需要持久化、需要现场配置的内容进入 `Flash` 结构体；不需要持久化修改的内容保留为工程静态参数。

##### 串口配置接口

当前配置模式下，串口接口使用 `USART1`。

当前串口配置接口只面向基础设备配置结构体开放，外部可配置项先限定为以下三项：

- 短 `PAN` 地址
- `ID` 地址
- 当前模式：`Anchor` / `Tag`

当前交互流程先定义为：

1. 串口接收到合法配置数据后，返回 `ok`，表示已收到
2. 串口接收到写入命令后，执行 Flash 写入
3. Flash 写入成功，返回 `succeed`
4. Flash 写入失败，返回 `failed`
5. 串口接收到读取命令后，返回当前 Flash 中保存的配置信息

从接口定位上看，这一组串口命令主要承担三类功能：

- 配置数据下发
- 当前配置读取
- Flash 持久化写入

具体命令格式、数据编码方式和串口报文约定，后续章节再单独细化。

##### 按键辅助逻辑

配置模式下，按键除用于进入配置模式外，还预留短按/长按功能：

- 短按：可作为读取或刷新当前配置状态的辅助触发方式
 - 暂时只作为读取的命令，会从flash中读取配置信息，并发送到串口上
- 长按：做长短按检测，在长按后松手时触发软复位

这里先保留功能定义，具体触发阈值和交互细节后续再补充。

##### ID 与灯光的辅助表达

当前对 `ID` 地址的使用先约定如下：

- 基站地址范围计划设置为 `0x30 ~ 0x40`

同时，板上 4 个指示灯还承担基础状态表达作用：

- 全亮：表示当前设备为 `Tag`
- 全灭：表示当前id设置不合法，不是作为错误，这个配置信息在串口上返回错误，灯灭没办法判断是否正常工作的

关于 `0x30`、`0x40` 与错误状态、`Tag` 状态之间的更细对应关系，当前先保留这个设计方向，后续再统一整理成明确的状态编码规则。

这里是因为灯亮表示1，灯灭表示0，所以可以使用0001~1110，表示14个状态，用来表示灯的id，但是由于灯的id我想设置成0x30~0x40之间的数据，所以这里加上这个偏置

因此，配置模式在当前阶段先建立以下几项核心能力：

- 进入条件明确
- 流水灯提示明确
- 串口配置入口明确
- Flash 写入流程明确
- 按键辅助控制预留明确

#### 3. 运行模式

运行模式是系统的正常工作路径，当前在本章中只保留总体说明，不展开具体实现细节。

这一模式主要负责：

- 读取配置
- 根据配置选择角色
- 启动 RTOS 任务
- 进入多源传感器数据采集与存储流程

运行模式中的详细任务组织、数据链路、时间同步和存储逻辑，统一放到后续章节展开。

## 6. 配置管理现状

这一章用于说明当前工程中配置管理的组织方式。按照前面已经确定的重构方向，后续配置管理不再把所有参数混在一个结构体中，而是拆分为“可持久化基础配置”和“静态外部参数”两部分。

当前配置管理的实现入口仍然位于：

- `APP/common/app_config.h`
- `APP/common/app_config.c`

后续重构时，可在保持接口连续性的前提下，再逐步拆分到更清晰的目录结构中。

### 6.1 配置分层

当前配置管理建议按两类配置组织：

#### 1. 基础设备配置

这一部分配置作为设备运行所必需、并且需要在现场修改的参数，最终写入 `Flash` 保存。

建议包含的内容为：

- 短 `PAN` 地址
- `ID` 地址
- 当前角色：`Anchor` / `Tag`

这一部分配置由配置模式下的串口接口负责修改，并在收到写入命令后持久化到 `Flash`。

#### 2. 静态外部参数

这一部分参数不写入 `Flash`，而是单独放在 `.h` 文件中，以静态变量形式存在，由系统直接读取使用。

这一类参数主要用于：

- 不需要现场频繁修改的系统参数
- `UWB` 相关扩展配置
- 工程内部固定参数

也就是说，后续配置管理在逻辑上分成两部分：

- 基础设备配置：可修改、可读取、写入 `Flash`
- 静态外部参数：工程静态定义、系统直接调用、不参与现场写入

### 6.2 配置管理流程

按照当前已经确定的逻辑，配置管理流程应理解为：

1. 系统上电后进入 `Boot`
2. 若进入配置模式，则通过 `USART1` 接收基础设备配置
3. 串口只对基础设备配置开放修改能力
4. 接收到写入命令后，将基础设备配置写入 `Flash`
5. 静态外部参数不参与串口配置，也不写入 `Flash`
6. 系统进入运行模式后，同时读取：
   - `Flash` 中的基础设备配置
   - 头文件中的静态外部参数

这样组织后，配置边界会比较清晰，也便于后续维护和扩展。

### 6.3 Flash 配置存储位置

当前基础设备配置的 `Flash` 存储位置为：

- Bank: `FLASH_BANK_1`
- Sector: `FLASH_SECTOR_7`
- Address: `0x080E0000`

这一部分用于保存设备基础配置，也就是后续通过串口配置并写入的那一组参数。

### 6.4 当前默认基础配置

从当前代码实现看，默认基础配置可归纳为：

- `PAN ID = 0xF0F0`
- `short_addr = 0x0034`
- `device_role = Anchor`

这部分属于默认基础设备配置，主要用于首次启动或 `Flash` 中配置无效时的回退。

### 6.5 配置管理的后续整理方向

后续在代码重构时，配置管理建议按以下方向逐步落实：

- 将基础设备配置结构体与静态外参结构体彻底分离
- 串口配置接口仅操作基础设备配置
- 读取命令仅返回 `Flash` 中实际保存的基础设备配置
- 静态外参保持为工程内部配置，不对外暴露写入接口

这样可以保证配置系统职责单一，避免后续把“设备身份参数”和“系统静态外参”重新混在一起。

因为设备身份id在整个程序的使用过程中，是不会发生变化的，所以和静态参数放在一起比较好，只是静态的参数不开放写的权限罢了

## 7. RTOS 设计

当前 RTOS 任务创建入口仍位于 `Core/Src/freertos.c`，但按照现在的设计思路，后续 RTOS 组织方式需要进一步调整，使任务职责更清晰、线程边界更明确。

### 7.1 设计目标

当前 RTOS 设计调整的重点，不是单纯增减线程数量，而是把各线程的职责重新梳理清楚。整体目标包括：

- 监控线程、采样线程、接收处理线程、写入线程分开
- 时间基准初始化收敛到统一线程中处理
- 采样线程只负责采样与数据打包
- 存储链路拆分为“接收整理”和“实际写卡”两个阶段
- 线程之间通过消息队列和共享缓存区协作

### 7.2 当前任务调整方向

#### 1. `defaultTask`

`defaultTask` 后续不再作为空转线程使用，而是作为系统监控线程保留。

当前希望它承担的职责包括：

- 监控其他线程是否正常工作
- 完成部分基础后台管理功能
- 启动 `TIM16` 相关时基能力

同时，该线程的优先级后续应调整为较低等级，不再维持之前较高优先级的设计。

#### 2. `InitTask`

`InitTask` 后续不再保留。

原因是当前 `TIM16` 的使用目的主要是提供硬件时间基准，这类初始化工作可以收敛到 `defaultTask` 或统一的系统初始化流程中完成，没有必要再单独保留一个专门的初始化线程。

#### 3. `DW1000samplingtask`

`DW1000samplingtask` 仍然作为 `UWB` 主任务保留。

该任务主要负责：

- 根据设备角色切换 `Tag` 或 `Anchor` 状态机
- 完成 `DW1000` 数据收发与测距流程
- 输出 `UWB` 数据节点

由于这一部分逻辑较重、状态机复杂，后续建议单独成章描述，不在本节展开细节。

#### 4. `IMUTask`

`IMUTask` 继续保留为 IMU 采样线程。

当前定义为：

- 由 IMU 中断触发采样
- 完成 IMU 传感器数据采集
- 当前采样频率按 `208 Hz` 设计

本节先不展开具体配置细节，保持当前驱动配置复制可用即可。

#### 5. `GNSSTask`

`GNSSTask` 继续保留为 GNSS 接收与解析线程。

该任务主要负责：

- 接收 GNSS 二进制数据流
- 完成协议解析
- 输出 GNSS 数据节点

这里需要强调一点：GNSS 原始数据在解析后不应人为降低精度。也就是说，输入是什么数据精度，输出就应保留什么精度，不能在处理中擅自截断到固定小数位。

#### 6. 存储相关线程

当前 `SDMMCTask` 的职责后续需要拆分和优化。

设计上不建议让单个线程同时承担“接收数据、排序整理、缓存管理、实际写卡”全部工作，而应拆分为两部分：

- 数据接收/整理线程
  - 负责从消息队列接收数据节点
  - 负责小规模排序和缓存管理

- SD 写入线程
  - 只负责将共享缓存区中的数据写入 SD 卡

这样可以使写卡线程职责单一，减少存储链路中的逻辑耦合。

### 7.3 数据在线程间的流转方式

按照当前你的调整思路，数据流转应组织为以下形式：

1. 采样线程获取各自的数据
2. 采样线程将“时间戳节点 + 自身数据节点”打包
3. 打包后的数据发送到消息队列
4. 接收整理线程从消息队列读取数据
5. 接收整理线程做一个小规模排序，当前规模先按约 `10` 帧设计，后续可调
6. 当共享缓存区达到半满状态后，通知写入线程开始写卡

这种设计下，采样、整理、写入三段职责会更清晰，也便于后续进一步优化吞吐和时序。

### 7.4 关于缓存写入的处理原则

按照当前思路，共享缓存区在写入过程中，大概率会遇到一帧数据跨越缓存边界的情况。

这一点当前先按简单原则处理：

- 如果一帧数据在缓存尾部被截断，不强行在当前位置拼成完整帧
- 直接向后写入
- 剩余数据在下一个包开始处继续写入

也就是说，当前阶段先保证数据连续落盘，不优先追求缓存边界上的帧完整对齐。后续若需要更严格的文件格式约束，再单独优化这一部分。

### 7.5 角色相关行为

设备角色来自基础设备配置，也就是 `Flash` 中保存的角色参数。

当前从系统设计角度可先理解为：

- 如果设备角色是 `Tag`
  - 启动完整的数据采集与存储流程
  - 包括 `UWB`、`IMU`、`GNSS` 以及存储相关线程

- 如果设备角色是 `Anchor`
  - 以 `UWB` 相关功能为主
  - 其他线程是否启动，后续应按最终设计再明确，而不再沿用当前“注释或置空”的临时方式

### 7.6 本章定位

这一章主要用于先把 RTOS 的职责划分和线程设计方向说明清楚，不在这里直接展开每个线程的具体实现细节。后续章节中，再分别细化：

- `UWB` 线程逻辑
- `GNSS` 线程逻辑
- `IMU` 线程逻辑
- 数据接收整理线程
- SD 写入线程

## 8. 数据采集链路

### 8.1 IMU 链路

相关文件：

- `APP/task/imusamplingtask.c`
- `APP/Bsp/bsp_asm330.c`
- `Thrid/asm330/*`

当前行为：

1. `SPI1` 初始化 `ASM330`
2. 配置输出速率为 `208Hz`
3. 使能加速度计和陀螺仪数据就绪中断
4. 外部中断到来时，通过 `vTaskNotifyGiveFromISR()` 通知 `IMUTask`
5. 任务读取 6 轴原始数据
6. 为数据打上全局时间戳
7. 投递到 `xIMUDataQueue`

当前 IMU 数据结构为：

- `imu_record_t`
  - `utc_global_timestamp_t ts`
  - `IMUOrigData_t data`

### 8.2 GNSS 链路

相关文件：

- `APP/task/UM960samplingtask.c`
- `APP/GNSS/gnss_parser.c`

当前行为：

1. `USART3 + DMA` 接收 GNSS 模块输出
2. 通过 `IDLE` 中断判断一帧接收结束
3. 将数据块交给 `gnss_parser`
4. 解析带 `0xAA 0x44 0xB5` 头的二进制协议
5. 当前重点处理消息 `0x0846`
6. 提取定位解算结果，并同时用 GNSS 时间更新系统时间基准
7. 投递到 `xUM960SamplingQueue`

当前输出结构为：

- `gnss_fusion_record_t`
  - `utc_global_timestamp_t ts`
  - `gnss_fusion_msg_t data`

### 8.3 UWB 链路

相关文件：

- `APP/task/DW1000samplingtask.c`
- `APP/UWB/*`
- `Thrid/decadriver/*`

当前行为：

1. 从 `AppConfig` 加载本机 `PAN ID / short_addr / role`
2. 初始化 DW1000 芯片和底层参数
3. 根据角色进入不同状态机：
   - `Tag`：主动轮询 Anchor，完成双向测距
   - `Anchor`：响应 Poll，回传时间戳与自身位置
4. 使用 DW1000 中断驱动收发状态切换
5. 在 `Tag` 侧计算距离
6. 读取 CIR/信号质量相关数据
7. 投递到 `xDW1000DataQueue`

当前 UWB 结果结构为：

- `uwb_result_queue_item_t`
  - 全局时间戳
  - `anchorId`
  - `tagId`
  - `distance_m`
  - `fpp_dbm`
  - `rxp_dbm`
  - `diff_db`
  - `accum_data[25]`

### 8.4 当前 Anchor 表

当前 `Tag` 侧轮询 Anchor 的表是**硬编码**的，定义在 `DW1000samplingtask.c`：

- `0x0032`
- `0x0033`
- `0x0034`
- `0x0035`

这意味着当前系统并不是“完全配置驱动”的，仍然保留明显的实验性质硬编码。

## 9. 时间同步机制现状

相关文件：

- `APP/common/timestamp.h`
- `APP/common/timestamp.c`

当前时间体系是一个“GNSS 驱动的全局时间戳”：

1. GNSS 数据报文提供周、周内毫秒、闰秒等信息。
2. `PPS` 上升沿到来时，更新全局时间基准。
3. `TIM16` 作为本地高分辨率计数器，用于补足毫秒内的细分时间。
4. `gettimestamp()` 返回：
   - `week`
   - `tow_ms`
   - `us`

也就是说，当前系统意图实现：

- GNSS 提供“绝对时间基准”
- 本地定时器提供“毫秒内细分”
- IMU / GNSS / UWB 共用统一时间戳结构

这部分是后续重构时非常值得保留的核心能力。

## 10. SD 存储现状

相关文件：

- `APP/task/SDcardtask.c`
- `FATFS/*`

当前行为：

1. 通过 `PB5` 检查 SD 卡是否存在
2. 初始化 `SDMMC1 + FatFs`
3. 挂载文件系统，必要时格式化
4. 创建/覆盖文件 `data_log.bin`
5. 不断从 `IMU / GNSS / UWB` 队列取数
6. 放入内部日志队列 `g_log_queue`
7. 以 ASCII 文本形式拼接日志行
8. 使用双缓冲分块写入 SD

### 10.1 当前写入格式

虽然文件名是 `data_log.bin`，但当前实际写入内容主要是**文本日志**，例如：

- `IMU ...`
- `RTK ...`
- `UWB ...`

所以从现状上看：

- 文件扩展名偏“二进制”
- 实际内容偏“ASCII 调试日志”

这说明 SD 存储格式目前还没有完全稳定下来。

### 10.2 当前队列/缓冲思路

当前存储链路采用了两层缓冲：

1. FreeRTOS 数据队列
2. SD 写入双缓冲

另外还存在一个按时间排序的 `LogQueue`，用于在写盘前粗略按时间排序。

## 13. 当前工程的主要问题

下面这些内容不是“批评”，而是后续重构最值得优先处理的地方。

### 13.1 模块职责边界不清晰

- `main.c` 里同时处理启动、配置、Boot 模式、日志输出
- `freertos.c` 里承担了较多业务判断
- 中断回调、驱动、任务之间大量通过全局变量直接耦合

### 13.2 硬编码较多

- Anchor 地址表硬编码
- 多个引脚、状态机常量、延时参数直接写死
- 部分默认参数没有集中配置中心

### 13.3 数据格式未稳定

- SD 文件名是 `.bin`，实际写的是 ASCII 文本
- 代码中同时保留了二进制打包思路和文本输出思路
- 最终落盘协议还没有完全定型

### 13.4 时间同步与采样流程耦合

- GNSS 解析、PPS、TIM16 计时、任务打时间戳耦合较深
- 后续若扩展更多传感器，时间基准模块应当独立

### 13.5 中断与任务通知关系分散

- IMU、DW1000、GNSS 分别采用不同触发方式
- 触发逻辑分散在多个文件
- 对系统行为的理解成本偏高

### 13.6 CubeMX 生成代码与手写代码混杂

- 当前结构可运行，但长期维护时容易出现：
  - 重新生成代码覆盖用户逻辑
  - 业务逻辑侵入 `Core/`
  - 硬件初始化边界不清晰

## 14. 建议的重构方向

后续重构建议优先围绕以下目标展开：

1. 明确分层
   - `board / drivers / services / app`

2. 抽离统一配置中心
   - 设备角色
   - UWB 参数
   - 传感器使能
   - 存储策略

3. 抽离统一时间服务
   - GNSS 时间输入
   - PPS 校准
   - 本地高精度计时
   - 对外统一 API

4. 统一采集接口
   - IMU/GNSS/UWB 都输出标准化数据帧

5. 明确存储协议
   - 最终确定写盘格式是二进制还是文本
   - 若是二进制，需要正式定义帧头、版本、长度、校验

6. 降低中断耦合
   - 中断只做最小通知
   - 状态机和数据组包全部下沉到任务上下文

7. 尽量把业务代码从 `Core/` 移出
   - 让 `Core/` 主要保留 CubeMX 自动生成内容

   - `config service`
   - `time service`
   - `sensor service`
   - `storage service`
4. 最后再重写任务编排和数据通道。
