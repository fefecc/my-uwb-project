# 本地时钟偏移量方案

## 目标

将全局时间系统调整为两阶段模型：

1. `PPS` 同步时只更新一次全局 `UTC offset`
2. 采集线程只采样“本地单调时钟 + offset 快照”
3. 排序线程统一解析 `UTC` 并格式化输出
4. `SD writer` 线程只负责块写入，不参与任何时间计算

这样可以把时间换算从“每次取时间都做锚点差值”改成“同步时更新 offset，使用时只取快照，输出时再统一解析”。

## 现状问题

当前实现位于 [time_service.c](../../APP/service/time_service.c)，基本路径是：

```text
PPS 时:   记录锚点 (local_anchor, utc_anchor)
查询时:   delta = local_now - local_anchor
          utc_now = utc_anchor + delta
```

现有问题有三类：

1. `TimeService_GetTimestamp()` 每次都要重新做本地时间读取、锚点差值计算和 `UTC` 拼接，查询路径冗余。
2. 生产线程过早得到最终 `UTC`，后续排序和写盘线程拿到的已经是“解析后的时间”，不利于统一时间职责。
3. 时间精度当前来自 `TIM16 20kHz`，但若过早压成整数毫秒，会直接丢失 `50us` 分辨率。

## 新方案

### 核心思路

内部统一时间基准改为 `TIM16 20kHz tick`，不再把高精度本地时间提前压成 `uint64_t local_ms`。

```text
PPS 时:
  utc_offset_tick_20k = utc_tick_20k_at_pps - local_tick_20k_at_pps

采样时:
  capture = { local_tick_20k, utc_offset_tick_20k, utc_valid, sync_state, sync_seq }

输出时:
  utc_tick_20k = capture.local_tick_20k + capture.utc_offset_tick_20k
```

其中：

- `PPS` 中断只更新全局 `offset`
- 采集线程只抓取“当前本地 tick + 当前 offset 快照”
- 排序线程统一把快照解析成标准 `TimeTimestamp`

### 本地单调时间基准

`TIM16` 配置保持不变：

| 参数 | 值 | 说明 |
|------|----|------|
| 时钟源 | 240 MHz (APB2) | STM32H743 |
| Prescaler | 11999 | `240MHz / 12000 = 20kHz` |
| Period (ARR) | 19999 | `20000 tick = 1s` |
| 溢出中断 | 1 Hz | `g_local_sec_count++` |

内部统一使用：

```text
local_tick_20k = sec_count * 20000 + CNT
```

性质：

- 单位是 `20kHz tick`
- 分辨率 `50us`
- 自开机起单调递增
- 排序、UWB 帧时刻、offset 全部以这个单位表达

### 时间快照结构

两份时间相关文档统一使用下面的目标接口口径：

```c
typedef struct {
    uint64_t local_tick_20k;
    int64_t  utc_offset_tick_20k;
    bool     utc_valid;
    TimeSyncState sync_state;
    uint32_t sync_seq;
} TimeCapture;
```

新增接口：

```c
bool TimeService_CaptureNow(TimeCapture *out);
bool TimeService_ResolveCapture(const TimeCapture *cap, TimeTimestamp *out);
```

语义约束：

- `TimeService_CaptureNow()`：原子采样当前 `local_tick_20k` 和当前 `offset` 快照
- `TimeService_ResolveCapture()`：把一个固定快照解成最终 `TimeTimestamp`
- `TimeService_OnPpsIrq()`：只更新全局 `utc_offset_tick_20k`、`utc_valid`、`sync_seq`

## 线程职责

### 采集线程

所有生产者线程（`GNSS`、`IMU`、`UWB`）统一行为：

1. 采集各自业务数据
2. 调用 `TimeService_CaptureNow()`
3. 将 `TimeCapture` 随 `AppDataNode` 一起入队

采集线程不直接产出最终 `UTC`。

### 排序线程

`AppDataSortTask` 负责：

1. 按 `time_capture.local_tick_20k` 排序
2. 调用 `TimeService_ResolveCapture()` 解析 `UTC`
3. 生成标准文本格式
4. 把最终文本写入 `SD FIFO`

时间换算在这里完成，写入缓存区后的字节即为最终输出内容。

### SD 写入线程

`AppSdWriterTask` 只负责：

1. 取出准备好的缓存块
2. 调用 `StorageService_WriteBlock()`
3. `f_sync()`
4. 释放块

它不读取时间服务，不转换 `UTC`，也不修改文本内容。

## 输出层适配

### 队列中的时间字段

`AppDataNode` 入队时携带 `TimeCapture`，不是最终 `TimeTimestamp`。

换句话说：

- 队列里存的是“原始时间快照”
- 不是“已经解析好的 `UTC`”

### SD 文本记录

`SD` 文本记录统一保留以下部分：

1. 本地单调时钟
2. `UTC` 时钟
3. 消息来源
4. 数据负载

这些字段在排序线程中一次性格式化完成；之后 `SD writer` 只写最终文本块。

### 串口日志

串口日志保持本地单调时钟前缀，不输出 `UTC` 字段。

要求：

- 日志时间语义仍然是“本地单调时钟”
- 不在串口日志中附带 `UTC`
- 排查系统时间问题时，以 `TimeCapture`/排序线程输出为准，不依赖串口日志做 `UTC` 对齐

## 与现有接口的关系

`TimeService_GetTimestamp()` 可以保留为兼容接口，但不再作为新数据链路的主入口。

新的推荐路径是：

1. 采集线程调用 `TimeService_CaptureNow()`
2. 排序线程调用 `TimeService_ResolveCapture()`

这样可以明确区分“采样时刻”和“输出时刻”，避免在采集路径上重复做 `UTC` 计算。

## 实施范围

本方案对应的实现修改会涉及：

- `APP/service/time_service.c/.h`
- `APP/common/app_types.h`
- `APP/task/app_tasks.c`
- 各采集线程对 `AppDataNode` 的赋时方式

## 不再采用的做法

以下做法在新方案中不再成立：

- 每次 `GetTimestamp` 都直接解出最终 `UTC`
- 内部时间基准使用 `uint64_t local_ms`
- `SD writer` 线程负责 `UTC` 换算
- 通过读取“当前全局 offset”来回填历史样本的 `UTC`

历史样本必须使用采样当时随样本一起保存的 `offset` 快照。
