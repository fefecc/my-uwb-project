# UWB PHY 运行态与超时设计

## 1. 设计目标

这份文档记录 PHY 层当前的设计收敛结果，重点只有两件事：

1. `g_phy` 只保留运行态，不再承载可变配置副本。
2. 除监听模式外，所有需要等待对端响应的阶段统一按 50ms 处理超时。

这里的“超时”指协议阶段的等待窗，不是线程队列超时，也不是数据会话总超时。

---

## 2. 运行态边界

### 2.1 启动期只读配置

以下字段属于启动期只读配置，不应作为 PHY 运行态长期保存：

- `pan_id`
- `short_addr`
- `role`
- `frame_ctrl`

这些值由系统启动阶段统一加载，PHY 只接收一份只读配置视图，用于帧构造和地址判断，不负责动态修改。

### 2.2 `g_phy` 只保存运行态

`g_phy` 只保存 PHY 线程运行时必须维护的状态，例如：

- 当前状态机状态
- 窗口 ID
- 线程句柄
- RX 窗口参数
- TX 后续待开启的 RX 参数
- 快速应答上下文
- 硬件错误计数

不建议再把 `pan_id / short_addr / role / frame_ctrl` 放进 `g_phy`，因为这些字段不参与运行态切换，只参与帧构造。

---

## 3. 超时模型

### 3.1 两类超时

当前需要区分两种超时：

1. **线程/命令级看门狗**
   - 用于保证 LINK/PHY 命令链路不永久挂住。
   - 这是现有保护，不和阶段等待窗混用。

2. **协议阶段等待窗**
   - 用于发送完成后等待对端响应。
   - 这里统一按 50ms 处理。

### 3.2 监听模式

监听模式不设置超时。

- 进入监听后，PHY 保持持续接收。
- 对应实现语义是 `dwt_setrxtimeout(0)`。

### 3.3 阶段超时表

以下表格描述的是“发起侧等待对端回包”的协议阶段。

| 阶段 | 触发点 | 超时 | 说明 |
|---|---:|---:|---|
| Discovery | 发送 `DISCOVERY_REQ` 后等待 `DISCOVERY_ACK` | 50ms | Discovery 当前应答槽本身有足够余量，50ms 作为统一初值合理 |
| Ranging | 发送 `RANGING_REQ` 后等待 `RANGING_RESP` | 50ms | 统一为和 Discovery 同级的阶段等待窗 |
| Data Prep | 发送 `DATA_PREP_REQ` 后等待 `DATA_PREP_ACK` | 50ms | 用于快速判定对端是否进入数据会话准备态 |
| Data Pull | 发送 `DATA_PULL_REQ` 后等待 `DATA_FRAGMENT` 或 `BUSY` | 50ms | 用于单片拉取与忙闲判断 |
| Data Done | 发送 `DATA_DONE` 后等待 `DATA_DONE_ACK` | 50ms | 用于结束确认和资源释放 |
| Listening | 常驻监听 | 不设置 | 该模式不启动阶段等待窗 |
| Data Session | 整个数据会话生命周期 | 5000ms | 这是会话级总超时，和单帧等待窗分开 |

### 3.4 现有看门狗与阶段等待窗的关系

现有代码里还保留了线程级兜底超时，例如：

- `UWB_LINK_PHY_TIMEOUT_MS = 30ms`
- `UWB_PHY_CMD_TIMEOUT_MS = 30ms`

它们的语义是“命令或终态事件没有按期回来就判异常”，和上表里的 50ms 阶段等待窗不是同一个层次。

---

## 4. 50ms 合理性

50ms 作为第一版统一值是合理的，理由如下：

- Discovery 的应答槽当前是 4ms 起步、5ms 级间隔，典型 8 槽场景的最晚应答大约在 39ms 左右，50ms 仍有余量。
- Ranging 和 Data 的单次响应通常比 Discovery 更短，50ms 足够覆盖正常空口、排队和轻微抖动。
- 这个值偏保守，适合先把阶段失败快速收敛起来，后续如果需要更快反馈，可以再单独收紧。

结论：**50ms 适合作为当前阶段的统一默认值**。

---

## 5. 约定

- 本文档只定义设计边界，不修改代码。
- 后续实现时，PHY 只读取启动期配置，不再维护配置副本。
- 后续实现时，非监听阶段的等待窗应统一按 50ms 收敛。
